# Closures in Rust: `Fn`, `FnMut`, `FnOnce` & the `move` Keyword

**Estimated reading time: ~40 minutes**

## What Is a Closure?

A closure is an anonymous function that **captures variables from its enclosing scope**. Unlike regular functions (`fn`), closures can reference local variables from the surrounding environment.

```rust
let name = String::from("Rust");
let greet = || println!("Hello, {name}!");
greet(); // prints: Hello, Rust!
```

The closure `greet` **captures** `name` from the outer scope. The compiler generates an anonymous struct to hold the captured variables and implements one or more of the three closure traits on it.

---

## The Three Closure Traits

Rust has three traits that describe how a closure can be called. They form a strict hierarchy:

```
FnOnce  ⊇  FnMut  ⊇  Fn
```

Every closure implements `FnOnce`. Some also implement `FnMut`. Fewer also implement `Fn`. A closure gets the **most permissive** trait that its body allows.

### `FnOnce` — call by consuming `self`

```rust
pub trait FnOnce<Args> {
    type Output;
    fn call_once(self, args: Args) -> Self::Output;
}
```

- Takes `self` **by value** — the closure is consumed when called.
- Can only be called **once**.
- Every closure implements this trait, because every closure can be called at least once.
- Required when the closure body **moves out of** a captured variable.

```rust
let name = String::from("Rust");
let consume = || {
    let _moved = name; // moves `name` out of the capture
    println!("consumed");
};
consume();
// consume(); // ERROR: closure already consumed (moved `name` out)
```

### `FnMut` — call by exclusive (`&mut`) reference

```rust
pub trait FnMut<Args>: FnOnce<Args> {
    fn call_mut(&mut self, args: Args) -> Self::Output;
}
```

- Takes `&mut self` — the closure can mutate its captured state.
- Can be called **multiple times**, but requires a mutable binding.
- Implemented when the closure **mutates** captured variables but does not move out of them.

```rust
let mut count = 0;
let mut increment = || {
    count += 1; // mutates captured `count`
};
increment();
increment();
println!("{count}"); // 2
```

### `Fn` — call by shared (`&`) reference

```rust
pub trait Fn<Args>: FnMut<Args> {
    fn call(&self, args: Args) -> Self::Output;
}
```

- Takes `&self` — the closure only reads its captured state (or captures nothing at all).
- Can be called **multiple times**, from **multiple threads** (if the captures are `Sync`).
- Implemented when the closure only **reads** captured variables (or captures nothing).

```rust
let name = String::from("Rust");
let greet = || println!("Hello, {name}!"); // only reads `name`
greet();
greet(); // fine — greet is Fn
```

### Trait hierarchy summary

| Trait | Receiver | Times callable | Closure body can... |
|-------|----------|----------------|---------------------|
| `FnOnce` | `self` | Once | Move out of captures |
| `FnMut` | `&mut self` | Many (needs `mut`) | Mutate captures |
| `Fn` | `&self` | Many | Only read captures |

Because of the supertrait chain (`Fn: FnMut: FnOnce`):
- If a function accepts `impl FnOnce(...)`, you can pass **any** closure.
- If a function accepts `impl Fn(...)`, you can only pass closures that don't mutate or move out of captures.

## How Closures Are Desugared

The compiler transforms every closure into an **anonymous struct** plus a trait implementation. This is the key to understanding Rust closures.

### Example: a simple `Fn` closure

```rust
fn main() {
    let x = 10;
    let add_x = |y| x + y;
    println!("{}", add_x(5)); // 15
}
```

The compiler desugars this into something equivalent to:

```rust
// Anonymous struct generated by the compiler (name is unnameable)
struct __ClosureAddX<'a> {
    x: &'a i32, // captured by shared reference
}

impl<'a> FnOnce<(i32,)> for __ClosureAddX<'a> {
    type Output = i32;
    fn call_once(self, (y,): (i32,)) -> i32 {
        self.x + y
    }
}

impl<'a> FnMut<(i32,)> for __ClosureAddX<'a> {
    fn call_mut(&mut self, (y,): (i32,)) -> i32 {
        self.x + y
    }
}

impl<'a> Fn<(i32,)> for __ClosureAddX<'a> {
    fn call(&self, (y,): (i32,)) -> i32 {
        *self.x + y
    }
}

fn main() {
    let x = 10;
    let add_x = __ClosureAddX { x: &x };
    println!("{}", add_x.call((5,))); // 15
}
```

**Key points:**
- The captured variable `x` becomes a **field** of the anonymous struct.
- Because the closure only reads `x`, it's captured **by shared reference** (`&i32`).
- The compiler implements all three traits (`Fn`, `FnMut`, `FnOnce`) since a closure that only reads can do everything.

### Example: an `FnMut` closure

```rust
fn main() {
    let mut count = 0;
    let mut inc = || { count += 1; };
    inc();
    inc();
}
```

Desugars to approximately:

```rust
struct __ClosureInc<'a> {
    count: &'a mut i32, // captured by mutable reference
}

impl<'a> FnOnce<()> for __ClosureInc<'a> {
    type Output = ();
    fn call_once(self, _: ()) {
        *self.count += 1;
    }
}

impl<'a> FnMut<()> for __ClosureInc<'a> {
    fn call_mut(&mut self, _: ()) {
        *self.count += 1;
    }
}

// NO Fn impl — the closure mutates state, so &self is insufficient.

fn main() {
    let mut count = 0;
    let mut inc = __ClosureInc { count: &mut count };
    inc.call_mut(());
    inc.call_mut(());
}
```

### Example: an `FnOnce` closure

```rust
fn main() {
    let name = String::from("Rust");
    let consume = || {
        drop(name); // moves `name` out — can't call again
    };
    consume();
}
```

Desugars to approximately:

```rust
struct __ClosureConsume {
    name: String, // captured by value (moved in)
}

impl FnOnce<()> for __ClosureConsume {
    type Output = ();
    fn call_once(self, _: ()) {
        drop(self.name); // moves name out of self
    }
}

// NO FnMut impl — cannot move out of &mut self.
// NO Fn impl — cannot move out of &self.

fn main() {
    let name = String::from("Rust");
    let consume = __ClosureConsume { name };
    consume.call_once(());
}
```

### Capture mode selection rules

The compiler chooses the **least restrictive** capture mode for each variable:

| What the closure does with `x` | Capture mode | Struct field type |
|---------------------------------|-------------|-------------------|
| Reads `x` (and `x: Copy`) | By shared reference | `&T` |
| Reads `x` (and `x: !Copy`) | By shared reference | `&T` |
| Mutates `x` (`x += 1`) | By mutable reference | `&mut T` |
| Moves out of `x` (`drop(x)`, returns `x`) | By value (move) | `T` |

Since Rust 2021 (edition 2021), the compiler performs **disjoint capture** — it can capture individual fields of a struct rather than the whole struct:

```rust
struct Pair { a: String, b: String }

let pair = Pair { a: "hello".into(), b: "world".into() };
let closure = || println!("{}", pair.a); // only captures `pair.a`, not all of `pair`
drop(pair.b); // fine — pair.b was never captured
```

## The `move` Keyword: Why It Exists

### What `move` does

The `move` keyword **forces all captured variables to be captured by value** (moved into the closure struct), regardless of what the closure body does with them:

```rust
let x = 42;
let print_x = move || println!("{x}");
// Without `move`: closure captures &x (shared reference)
// With `move`: closure captures x by value (copies it, since i32: Copy)
```

```rust
let name = String::from("Alice");
let greet = move || println!("Hi, {name}");
// `name` is moved into the closure. `name` is no longer usable here.
// greet(); // works
// println!("{name}"); // ERROR: name was moved
```

### "The compiler can figure it out" — so why is `move` required?

This is a common source of confusion. The compiler picks the *minimal* capture mode for the closure body to work. If the body only reads a variable, the compiler captures by reference. This is correct **locally**, but there are situations where by-reference capture is wrong for the **broader program** — and the compiler intentionally does not automatically upgrade to by-value capture in those cases.

#### Reason 1: Returning closures from functions

A closure that captures by reference borrows from the local stack frame. If you return that closure, the references would dangle:

```rust
fn make_greeter(name: String) -> impl Fn() {
    // ERROR without `move`:
    // `name` is borrowed by the closure, but `name` is dropped
    // when this function returns → dangling reference.
    move || println!("Hello, {name}!")
}
```

**Why doesn't the compiler just infer `move`?** Because `move` changes semantics in the caller: after `move`, the original variable is gone. This is a *transfer of ownership*, and Rust's design philosophy is that ownership transfers must be **visible at the point of transfer**. Silent moves would make it unclear where a value's lifetime ends.

```rust
fn example(name: String) -> impl Fn() {
    // If the compiler silently moved `name` into the closure,
    // this line would fail — but it would be invisible WHY:
    // println!("{name}"); // would be an error with no visible `move`
    
    move || println!("Hello, {name}!")
    // The `move` keyword makes it explicit: name is consumed here.
}
```

#### Reason 2: Sending closures to other threads

When spawning a thread, the closure must own its data — references to the spawning thread's stack would dangle once the spawning thread's scope ends. `'static` is required:

```rust
use std::thread;

fn main() {
    let data = vec![1, 2, 3];
    
    // ERROR without `move`:
    // closure captures `&data`, but the thread might outlive `main`'s stack.
    let handle = thread::spawn(move || {
        println!("{data:?}");
    });
    
    handle.join().unwrap();
}
```

The compiler *does* give a helpful error if you forget `move` here, but it intentionally does not auto-insert it because:

1. **Ownership transfer must be explicit** — it changes what the outer scope can access.
2. **The programmer must decide** — maybe you *shouldn't* move the data; maybe you should `clone` it, or use `Arc`, or restructure the code.
3. **`move` affects all captures** — it moves *everything* referenced in the closure body, which may not be what you want.

#### Reason 3: `move` with `Copy` types — extending lifetime without losing the original

For `Copy` types, `move` copies the value into the closure instead of referencing it. This is useful when you want the closure to be self-contained:

```rust
fn make_adder(x: i32) -> impl Fn(i32) -> i32 {
    move |y| x + y  // `x` is copied into the closure (i32: Copy)
    // Without `move`: would try to capture &x → dangling after return
}
```

Even though `i32` is `Copy` and the "move" is really a copy, you still need the keyword. The compiler does not special-case `Copy` types to auto-promote because the decision between reference-capture and value-capture has semantic meaning for *all* captures in the closure, not just this one.

#### Reason 4: Async blocks

This is one of the most common places where `move` is essential. Async blocks return a `Future` that may be polled much later — any references it holds must remain valid across `.await` points:

```rust
async fn fetch_data(url: String) {
    let client = reqwest::Client::new();
    
    // The future may be moved to another thread, polled later, etc.
    let task = tokio::spawn(async move {
        // `async move` captures every used variable by value.
        // What happens to each depends on whether it implements Copy:
        //
        //   - `url`: String is !Copy  → MOVED into the future (original invalidated)
        //   - `client`: reqwest::Client is Clone but !Copy → MOVED (original invalidated)
        //
        // If Client *did* implement Copy, it would be COPIED (bitwise)
        // and the original `client` would remain valid after this block.
        // The `move` keyword doesn't distinguish — it always means
        // "capture by value," and Copy vs. !Copy determines whether
        // the original survives.
        client.get(&url).send().await
    });
    
    // Both `url` and `client` were moved (neither is Copy).
    // They are no longer available here.
}
```

### What `move` does NOT change

`move` only affects **how variables are captured** (by value vs. by reference). It does **not** change which closure trait is implemented:

```rust
let s = String::from("hello");

// Without move: captures &s, implements Fn
let a = || println!("{s}");

// With move: captures s by value, STILL implements Fn
// (because the body only reads s — it doesn't mutate or move out of it)
let b = move || println!("{s}");
```

Both `a` and `b` implement `Fn`. The difference is that `b` owns the `String`, while `a` borrows it.

| | Without `move` | With `move` |
|---|---|---|
| Capture mode | Minimal (compiler chooses) | Always by value |
| Trait implemented | Based on what body does | Based on what body does (same rules) |
| Original variable | Still usable (if borrowed) | Moved (unless `Copy`) |
| Closure lifetime | Tied to borrows | Self-contained (`'static` possible) |

## Desugaring `move` Closures

Revisiting the desugaring — `move` changes the struct fields from references to owned values:

### Without `move`:

```rust
let x = String::from("hello");
let closure = || println!("{x}");
```

```rust
struct __Closure<'a> {
    x: &'a String,  // borrowed
}
```

### With `move`:

```rust
let x = String::from("hello");
let closure = move || println!("{x}");
```

```rust
struct __Closure {
    x: String,  // owned — no lifetime parameter needed
}
```

The body of `call(&self)` remains the same — it reads `self.x`. But the struct now **owns** the data, so the closure can be `'static` and sent across threads.

## Copy vs. Move into a Closure: The Exact Rule

When a variable is captured **by value** (either because of `move` or because the closure body moves out of it), one of two things happens. The rule is simple and absolute:

> **If `T: Copy`, the value is copied. If `T: !Copy`, ownership is transferred (moved).**

That's it. There is no separate analysis, no heuristic, no "sometimes." It is the same rule as regular assignment (`let b = a;`), just applied to the closure's capture struct fields.

### The decision tree

```
Is the variable captured by value?
├── NO (captured by reference: &T or &mut T)
│   └── No copy, no move. The closure borrows the variable.
│       The original variable is still valid (but may be locked by the borrow).
│
└── YES (either `move` keyword, or body moves out of variable)
    │
    ├── Does T implement Copy?
    │   ├── YES → The value is **copied** into the closure.
    │   │         The original variable remains valid and usable.
    │   │         Examples: i32, f64, bool, char, &T, *const T,
    │   │                   (i32, bool), [u8; 4]
    │   │
    │   └── NO  → The value is **moved** into the closure.
    │             The original variable is invalidated.
    │             Examples: String, Vec<T>, Box<T>, HashMap<K,V>,
    │                       any struct without #[derive(Copy)]
    │
    └── (There is no third option.)
```

### Concrete examples, side by side

```rust
// ═══════════════════════════════════════════════
// CASE 1: i32 — Copy type
// ═══════════════════════════════════════════════
let x: i32 = 42;
let f = move || println!("{x}");
println!("{x}");  // ✅ OK — x was COPIED into f. Original still valid.
f();

// ═══════════════════════════════════════════════
// CASE 2: String — non-Copy type
// ═══════════════════════════════════════════════
let s = String::from("hello");
let g = move || println!("{s}");
// println!("{s}"); // ❌ ERROR — s was MOVED into g. Original is gone.
g();

// ═══════════════════════════════════════════════
// CASE 3: &str (reference) — Copy type!
// ═══════════════════════════════════════════════
let r: &str = "hello";        // &str is Copy (it's a shared reference)
let h = move || println!("{r}");
println!("{r}");  // ✅ OK — r (the reference) was COPIED into h.
h();

// ═══════════════════════════════════════════════
// CASE 4: &String (reference to non-Copy) — still Copy!
// ═══════════════════════════════════════════════
let owned = String::from("world");
let ref_to_owned: &String = &owned;
let j = move || println!("{ref_to_owned}");
println!("{ref_to_owned}"); // ✅ OK — the *reference* was copied, not the String
j();

// ═══════════════════════════════════════════════
// CASE 5: Mixed captures — each variable independently
// ═══════════════════════════════════════════════
let n: i32 = 10;                    // Copy
let v: Vec<i32> = vec![1, 2, 3];   // NOT Copy
let k = move || println!("{n} {v:?}");
println!("{n}");   // ✅ OK — n was copied
// println!("{v:?}"); // ❌ ERROR — v was moved
k();
```

### The key insight: `move` does the same thing as `let b = a;`

The `move` keyword on a closure is equivalent to writing `let field = variable;` for each captured variable. And Rust's rule for `let b = a;` is:

| `T: Copy`? | What happens at `let b = a;` | What happens at `move` capture |
|-------------|------------------------------|-------------------------------|
| Yes | Bitwise copy. `a` remains valid. | Bitwise copy into closure struct. Variable remains valid. |
| No | Move. `a` is invalidated. | Move into closure struct. Variable is invalidated. |

There is **no difference** between the two situations. The closure is just a struct, and `move` is just assignment into its fields.

### Why this confuses people

The confusion usually comes from three sources:

**1. The word "move" suggests destruction, but `Copy` types survive.**

```rust
let x = 42i32;
let f = move || x;   // "moved" into closure
println!("{x}");      // but x is fine!
```

This feels contradictory until you realize: for `Copy` types, "move" and "copy" are the same operation (a bitwise memcpy). The original just isn't invalidated because the type opts into that behavior.

**2. References are `Copy`, which is non-obvious.**

```rust
let big_vec = vec![0; 1_000_000];
let r = &big_vec;
let f = move || println!("{}", r.len());
println!("{}", r.len()); // ✅ OK — only the reference (a pointer) was copied
```

`&T` is always `Copy`, regardless of what `T` is. Moving a `&Vec<i32>` into a closure copies the 8-byte pointer, not the million-element vector. But the closure now holds a `&Vec<i32>` with a lifetime — it cannot outlive `big_vec`.

**3. `move` + `Copy` reference ≠ owning the data.**

```rust
fn make_closure(data: &[i32]) -> impl Fn() + '_ {
    move || println!("{}", data.len())
    // `data` (&[i32]) is Copy — it's copied into the closure.
    // But the closure still borrows from the original slice!
    // The +'_ lifetime bound reflects this.
}

// This does NOT work:
// fn make_static(data: &[i32]) -> impl Fn() + 'static {
//     move || println!("{}", data.len())
//     // ERROR: `data` is &[i32] with a non-'static lifetime.
//     // Copying the reference doesn't extend the lifetime!
// }
```

`move` copies the *reference* by value, but the reference still points to borrowed data. To get `'static`, you need to move *owned* data (`Vec<i32>`, not `&[i32]`).

### Quick reference: common types and what happens with `move`

| Type | `Copy`? | `move` effect | Original after `move`? |
|------|---------|---------------|----------------------|
| `i32`, `f64`, `bool`, `char` | Yes | Copied | Valid |
| `&T` (any shared reference) | Yes | Copied (pointer) | Valid |
| `*const T`, `*mut T` | Yes | Copied | Valid |
| `(i32, bool)` | Yes | Copied | Valid |
| `[i32; 3]` | Yes | Copied | Valid |
| `Option<i32>` | Yes | Copied | Valid |
| `String` | No | Moved | **Invalidated** |
| `Vec<T>` | No | Moved | **Invalidated** |
| `Box<T>` | No | Moved | **Invalidated** |
| `HashMap<K, V>` | No | Moved | **Invalidated** |
| `Rc<T>`, `Arc<T>` | No | Moved | **Invalidated** |
| `&mut T` | No | Moved | **Invalidated** |
| `File`, `TcpStream` | No | Moved | **Invalidated** |
| Any struct with `Drop` | No | Moved | **Invalidated** |

Note: `&mut T` is **not** `Copy` (it's a unique reference — copying would create aliasing). So `move` transfers the mutable reference into the closure and invalidates the original binding.

## Closures and Trait Bounds in Practice

### Choosing the right trait bound

When writing functions that accept closures, pick the **most permissive** trait that your function needs:

```rust
// Most permissive — accepts any closure (but can only call it once)
fn call_once(f: impl FnOnce()) { f(); }

// Middle ground — can call multiple times, closure may mutate state
fn call_mut(mut f: impl FnMut()) { f(); f(); }

// Most restrictive — can call multiple times, shares freely
fn call_fn(f: impl Fn()) { f(); f(); }
```

**Rule of thumb:** Use `FnOnce` unless you need to call the closure more than once. Use `FnMut` if you call it multiple times. Use `Fn` only if you need shared/concurrent access.

### Common standard library usage

| Function | Trait bound | Why |
|----------|------------|-----|
| `Option::map` | `FnOnce(T) -> U` | Called at most once |
| `Iterator::map` | `FnMut(T) -> U` | Called per element, may mutate state |
| `Iterator::for_each` | `FnMut(T)` | Called per element |
| `thread::spawn` | `FnOnce() + Send + 'static` | Called once, must be sendable |
| `Vec::sort_by` | `FnMut(&T, &T) -> Ordering` | Called many times during sort |
| `Fn` pointers in structs | `Fn(...)` (usually boxed) | Shared access, called many times |

### `Box<dyn Fn(...)>` vs `impl Fn(...)`

```rust
// Static dispatch — monomorphized, zero-cost, but can't store heterogeneous closures
fn apply(f: impl Fn(i32) -> i32, x: i32) -> i32 { f(x) }

// Dynamic dispatch — trait object, heap-allocated, supports heterogeneous closures
fn apply_dyn(f: &dyn Fn(i32) -> i32, x: i32) -> i32 { f(x) }

// Owned trait object — can be stored in structs
struct Callback {
    f: Box<dyn Fn(i32) -> i32>,
}
```

## Function Pointers vs Closures

A function pointer (`fn(Args) -> Ret`) is a **separate type** from closures, but every `fn` item implements all three closure traits:

```rust
fn double(x: i32) -> i32 { x * 2 }

let f: fn(i32) -> i32 = double;     // function pointer
let g: &dyn Fn(i32) -> i32 = &double; // trait object

// fn pointers implement Fn, FnMut, and FnOnce
fn apply(f: impl Fn(i32) -> i32) -> i32 { f(5) }
assert_eq!(apply(double), 10);      // works
assert_eq!(apply(|x| x * 2), 10);   // also works
```

However, **closures that capture variables cannot be coerced to `fn` pointers**:

```rust
let offset = 10;
let add_offset = |x| x + offset; // captures `offset`

// ERROR: closure captures environment, cannot coerce to fn pointer
// let f: fn(i32) -> i32 = add_offset;

// This works — non-capturing closures CAN be coerced:
let mul2 = |x: i32| x * 2; // captures nothing
let f: fn(i32) -> i32 = mul2; // OK
```

## Closures and Lifetimes

### Closures borrowing local variables

A closure that captures by reference has an implicit lifetime tied to the borrowed data:

```rust
fn make_closure<'a>(s: &'a str) -> impl Fn() + 'a {
    move || println!("{s}")
    // Even though we use `move`, &str is Copy — it copies the reference.
    // The closure is bounded by 'a because it holds a &'a str.
}
```

### The `'static` bound

`'static` means the closure owns all its data (no borrowed references, or only `&'static` ones). `move` is typically how you achieve this:

```rust
fn spawn_task(f: impl FnOnce() + Send + 'static) {
    std::thread::spawn(f);
}

fn main() {
    let data = String::from("owned");
    spawn_task(move || {
        println!("{data}"); // data is moved in — closure is 'static
    });
}
```

## Formal Capture and `move` Rules (from the Rust Reference)

The rules governing closure captures and when `move` is required are not stated in a single place in the Rust Reference. They are spread across several sections and interact with lifetime/borrow checking. This section consolidates them.

> - [Closure expressions](https://doc.rust-lang.org/reference/expressions/closure-expr.html) — syntax, `move` keyword definition
> - [Closure types → Capture modes](https://doc.rust-lang.org/reference/types/closure.html#capture-modes) — capture precedence rules
> - [Drop scopes](https://doc.rust-lang.org/reference/destructors.html#drop-scopes) — when values are dropped relative to scope boundaries
> - [Trait and lifetime bounds](https://doc.rust-lang.org/reference/trait-bounds.html) — `'static`, `Send`, etc.
> - [Return-position `impl Trait`](https://doc.rust-lang.org/reference/types/impl-trait.html#abstract-return-types)
> - [Async blocks](https://doc.rust-lang.org/reference/expressions/block-expr.html#async-blocks)

### Rule 1: Capture mode precedence

Without `move`, the compiler selects the **least restrictive mode** for each captured place (variable or field), based on how the closure body uses it. The precedence, from least to most restrictive:

1. **Shared reference (`&T`)** — if the closure only reads the value.
2. **Unique immutable borrow** — a special intermediate mode (not directly expressible in surface Rust) used when the closure needs to mutably reborrow through an `&mut` reference it captured immutably. Example: the closure captures `&ref_to_mut` and calls a `&mut self` method through it.
3. **Mutable reference (`&mut T`)** — if the closure mutates the value.
4. **By value (move/copy)** — if the closure moves out of the value (e.g., `drop(x)`, passes `x` to a function taking ownership, or returns `x`).

The compiler analyzes the closure body and picks the minimum mode for each capture independently.

### Rule 2: `move` overrides capture mode to by-value

When `move` is present on the closure, **every** captured variable is taken by value, regardless of what the body does with it:

- If `T: Copy`, the value is **copied** — the original remains valid.
- If `T: !Copy`, the value is **moved** — the original is invalidated.

The `move` keyword does **not** affect which `Fn`/`FnMut`/`FnOnce` trait the closure implements — that is still determined solely by the closure body.

### Rule 3: Disjoint field capture (Edition 2021+, RFC 2229)

Starting with Rust Edition 2021, the compiler captures **individual fields** of structs/tuples rather than the whole variable, when possible:

```rust
struct S { a: String, b: String }
let s = S { a: "x".into(), b: "y".into() };
let c = || drop(s.a); // captures only `s.a`, not all of `s`
println!("{}", s.b);   // OK — `s.b` was never captured
```

Exceptions where the whole variable is captured:
- The closure uses a method that takes `self` or `&self`/`&mut self` on the variable itself.
- The variable is used in a pattern that binds the whole value.
- `move` closures: each *used* field is captured by value individually (but unused fields are not captured at all).

### Rule 4: Lifetime constraints on captures

The closure's **type** carries the lifetimes of everything it borrows. This creates constraints:

- If the closure captures `&'a T`, then the closure cannot outlive `'a`.
- If the closure captures `&'a mut T`, then the closure cannot outlive `'a`, and no other access to `T` is allowed while the closure exists.
- If the closure captures `T` by value (via `move` or because the body moves out of it), there is no lifetime constraint from that capture — the closure owns the data.

### Rule 5: When `move` is *required* by the type system

`move` is never inserted automatically. The compiler will emit an error and suggest `move` when the inferred captures (by reference) violate lifetime rules. The common situations:

#### 5a. Returning a closure from a function

The return type must outlive the function body. References to local variables do not:

```rust
fn make() -> impl Fn() {
    let x = String::from("hi");
    // ERROR: closure borrows `x`, but `x` is dropped at end of `make`
    // || println!("{x}")

    move || println!("{x}") // OK: `x` moved into closure
}
```

**Rule:** When a closure appears in return position and captures local variables, `move` is required (unless all captures are `'static` or `Copy` references that outlive the function).

#### 5b. `'static` bounds (threads, task spawning)

APIs like `std::thread::spawn` require `F: FnOnce() + Send + 'static`. A closure holding non-`'static` borrows fails this bound:

```rust
let data = vec![1, 2, 3];
// thread::spawn(|| println!("{data:?}")); // ERROR: `data` borrowed, not 'static

std::thread::spawn(move || println!("{data:?}")); // OK: data moved in
```

**Rule:** When a closure must satisfy a `'static` lifetime bound, any captured non-`'static` data must be moved into the closure with `move`.

#### 5c. Async blocks and futures

`async` blocks produce futures that may be `.await`ed much later or moved across threads. References to the enclosing stack frame would dangle:

```rust
let url = String::from("https://example.com");

// ERROR: future borrows `url`, but the future may outlive current scope
// tokio::spawn(async { println!("{url}"); });

tokio::spawn(async move { println!("{url}"); }); // OK
```

**Rule:** `async move { ... }` is required when the future must own its captures, which is nearly always the case for spawned tasks.

#### 5d. Closures stored in structs or `Box<dyn Fn(...)>`

When a closure is stored beyond the current scope, it must own its data:

```rust
struct Callback {
    f: Box<dyn Fn()>,
}

fn make_callback() -> Callback {
    let msg = String::from("clicked");
    Callback {
        // f: Box::new(|| println!("{msg}")), // ERROR: borrows local `msg`
        f: Box::new(move || println!("{msg}")), // OK: msg moved in
    }
}
```

#### 5e. Closures in `Iterator` adapters returned from functions

When the iterator (and its closure) is returned or stored beyond the current scope:

```rust
fn make_iter(data: Vec<i32>) -> impl Iterator<Item = i32> {
    let factor = 2;
    // factor is i32 (Copy), but without `move` it captures &factor
    // which borrows from this stack frame.
    data.into_iter().map(move |x| x * factor)
}
```

### Rule 6: When `move` is NOT required

- **Closures used locally** that don't escape the current scope — the compiler's default by-reference capture is fine.
- **Closures that capture only `'static` references** (e.g., `&'static str` literals) — already satisfy `'static`.
- **Closures that capture nothing** — equivalent to function pointers, inherently `'static`.
- **Closures where the body already moves the variable** — even without the `move` keyword, the capture is by value if the body moves out. However, adding `move` still gives the benefit of moving *all* captures by value, not just the ones the body moves.

### Why the compiler doesn't auto-insert `move`

The Rust Reference does not have a rationale section for this, but the design follows from Rust's core principle:

> **Ownership transfers must be visible at the point of transfer.**

Auto-inserting `move` would silently invalidate variables in the outer scope. The programmer must explicitly choose between:
1. `move` — transfer ownership (closure owns data, outer scope loses it).
2. `.clone()` + `move` — duplicate the data (both scopes retain their own copy).
3. `Arc`/`Rc` wrapping — share ownership via reference counting.
4. Restructuring — change the design so the closure doesn't need to outlive the scope.

The compiler's error messages actively suggest `move` when appropriate, but the decision belongs to the programmer because each option has different semantics, performance, and correctness implications.

## Edge Cases and Subtleties

### `move` closures that are still `Fn`

A `move` closure can implement `Fn` — `move` doesn't mean `FnOnce`:

```rust
let x = 42i32;
let f = move || x; // moves x (copies, since i32: Copy)
// f implements Fn — calling it just reads the internal copy of x
assert_eq!(f(), 42);
assert_eq!(f(), 42); // can call many times
```

### Closures that capture nothing

A closure capturing nothing is equivalent to a function pointer and implements all three traits:

```rust
let f = || 42;
// Implements Fn, FnMut, FnOnce
// Can be coerced to fn() -> i32
let fp: fn() -> i32 = f;
```

### Returning different closures from branches

Because each closure is a different anonymous type, you cannot return different closures from `if`/`else` without boxing:

```rust
fn pick(flag: bool) -> Box<dyn Fn(i32) -> i32> {
    if flag {
        Box::new(|x| x + 1)
    } else {
        Box::new(|x| x * 2)
    }
}
```

### Recursive closures

Closures cannot directly refer to themselves. You need a workaround:

```rust
use std::cell::RefCell;
use std::rc::Rc;

fn factorial() -> impl Fn(u64) -> u64 {
    let f: Rc<RefCell<Option<Box<dyn Fn(u64) -> u64>>>> = 
        Rc::new(RefCell::new(None));
    let f_clone = f.clone();
    *f.borrow_mut() = Some(Box::new(move |n| {
        if n == 0 { 1 }
        else { n * (f_clone.borrow().as_ref().unwrap())(n - 1) }
    }));
    let f_clone = f.clone();
    move |n| (f_clone.borrow().as_ref().unwrap())(n)
}
```

This is awkward by design — prefer regular `fn` for recursion.

### Mixed captures: which trait does the closure implement?

When a closure captures multiple variables with **different** capture modes, the implemented trait is determined by the **most restrictive** capture across all variables. The "bottleneck" capture wins.

#### Case 1: One read + one mutate → `FnMut`

```rust
let name = String::from("Alice");  // will be captured by &String (read)
let mut count = 0u32;              // will be captured by &mut u32 (mutate)

let mut closure = || {
    println!("{name}");  // reads `name` → &String
    count += 1;          // mutates `count` → &mut u32
};

closure();
closure();
println!("count = {count}"); // 2

// Trait implemented: FnMut (and FnOnce, since FnMut: FnOnce)
// NOT Fn — because the closure mutates `count`.
//
// Desugared struct:
// struct __Closure<'a, 'b> {
//     name: &'a String,      // shared reference (read only)
//     count: &'b mut u32,    // mutable reference (mutates)
// }
// → call_mut(&mut self) works, call(&self) does NOT (can't mutate through &self)
```

#### Case 2: One read + one move out → `FnOnce`

```rust
let x: i32 = 42;                      // will be captured by &i32 (read)
let data = vec![1, 2, 3];             // will be captured by value (moved out)

let closure = || {
    println!("{x}");       // reads `x` → &i32
    drop(data);            // moves out of `data` → Vec<i32> by value
};

closure();
// closure(); // ERROR: cannot call again — `data` was moved out

// Trait implemented: FnOnce ONLY
// NOT FnMut — cannot move out of &mut self.
// NOT Fn — cannot move out of &self.
//
// Desugared struct:
// struct __Closure<'a> {
//     x: &'a i32,        // shared reference
//     data: Vec<i32>,    // owned (by value — body moves out of it)
// }
// → call_once(self) works (consumes self, can move data out)
// → call_mut(&mut self) does NOT (can't move out of &mut self)
```

#### Case 3: One mutate + one move out → `FnOnce`

```rust
let mut counter = 0u32;
let name = String::from("hello");

let closure = || {
    counter += 1;           // mutates → &mut u32
    let _owned = name;      // moves out → String by value
};

closure();
// closure(); // ERROR: FnOnce only

// The mutation of `counter` would allow FnMut, but the move
// of `name` restricts to FnOnce. The most restrictive wins.
```

#### Case 4: `move` keyword + read-only body → still `Fn`!

```rust
let x: i32 = 42;              // Copy → will be copied
let s = String::from("hi");   // !Copy → will be moved

let closure = move || {
    // Both are captured by value (due to `move`), but the body
    // only READS them — no mutation, no moving out.
    println!("{x} {s}");
};

closure();
closure(); // ✅ OK — implements Fn

// `move` affects HOW variables enter the closure (by value).
// The TRAIT is determined by what the body DOES with the captures.
// Body only reads → Fn.
//
// Desugared struct:
// struct __Closure {
//     x: i32,       // copied (i32: Copy)
//     s: String,    // moved (String: !Copy)
// }
// → call(&self) reads self.x and self.s — works fine.
// → Implements Fn + FnMut + FnOnce.
```

#### Case 5: `move` keyword + mutate one → `FnMut`

```rust
let x: i32 = 42;
let mut buf = Vec::<i32>::new();

// Using `move` forces both to be captured by value.
let mut closure = move || {
    buf.push(x);  // mutates buf, reads x
};

closure();
closure();
// println!("{buf:?}"); // ERROR: `buf` was moved into closure

// Body mutates `buf` → FnMut.
// Body only reads `x` → doesn't restrict further.
// Result: FnMut (+ FnOnce).
//
// Desugared struct:
// struct __Closure {
//     x: i32,          // copied
//     buf: Vec<i32>,   // moved
// }
// → call_mut(&mut self) can mutate self.buf — works.
// → call(&self) cannot mutate self.buf — fails.
```

#### Summary: mixed captures → trait determined by worst case

| Capture A | Capture B | Body does with A | Body does with B | Trait implemented |
|-----------|-----------|------------------|------------------|-------------------|
| `&T` | `&U` | read | read | **Fn** + FnMut + FnOnce |
| `&T` | `&mut U` | read | mutate | **FnMut** + FnOnce |
| `&T` | `U` (by value) | read | move out | **FnOnce** only |
| `&mut T` | `&mut U` | mutate | mutate | **FnMut** + FnOnce |
| `&mut T` | `U` (by value) | mutate | move out | **FnOnce** only |
| `T` (by value) | `U` (by value) | read | read | **Fn** + FnMut + FnOnce |
| `T` (by value) | `U` (by value) | read | mutate | **FnMut** + FnOnce |
| `T` (by value) | `U` (by value) | read | move out | **FnOnce** only |

The rule: **the closure implements the most restrictive trait required by ANY of its captures' usage.**

### Compile-time trait checker for closures

You can use these helper functions to verify at compile time which `Fn` traits a closure implements. If the code compiles, the closure satisfies that trait. If it doesn't, the compiler error tells you exactly why.

```rust
/// Compiles only if `F` implements `Fn` (callable via &self).
fn assert_fn<F: Fn()>(_f: &F) {}

/// Compiles only if `F` implements `FnMut` (callable via &mut self).
fn assert_fn_mut<F: FnMut()>(_f: &F) {}

/// Compiles only if `F` implements `FnOnce` (callable via self).
fn assert_fn_once<F: FnOnce()>(_f: &F) {}

fn main() {
    // ── Test 1: Read-only closure ──────────────────────────
    let x = String::from("hello");
    let c1 = || println!("{x}");
    
    assert_fn(&c1);       // ✅ compiles
    assert_fn_mut(&c1);   // ✅ compiles (Fn implies FnMut)
    assert_fn_once(&c1);  // ✅ compiles (FnMut implies FnOnce)
    
    // ── Test 2: Mutating closure ───────────────────────────
    let mut count = 0;
    let mut c2 = || { count += 1; };
    
    // assert_fn(&c2);    // ❌ ERROR: the closure mutates `count`
    assert_fn_mut(&c2);   // ✅ compiles
    assert_fn_once(&c2);  // ✅ compiles
    
    // ── Test 3: Moving closure ─────────────────────────────
    let data = vec![1, 2, 3];
    let c3 = || { drop(data); };
    
    // assert_fn(&c3);    // ❌ ERROR: moves out of capture
    // assert_fn_mut(&c3);// ❌ ERROR: moves out of capture
    assert_fn_once(&c3);  // ✅ compiles
    
    // ── Test 4: `move` but read-only body ──────────────────
    let s = String::from("world");
    let c4 = move || println!("{s}");
    
    assert_fn(&c4);       // ✅ compiles — move doesn't mean FnOnce!
    assert_fn_mut(&c4);   // ✅ compiles
    assert_fn_once(&c4);  // ✅ compiles
}
```

#### Generic version with return types

```rust
/// Works with any signature — adjust the generics as needed.
fn assert_fn_with_args<A, R, F: Fn(A) -> R>(_f: &F) {}
fn assert_fn_mut_with_args<A, R, F: FnMut(A) -> R>(_f: &F) {}
fn assert_fn_once_with_args<A, R, F: FnOnce(A) -> R>(_f: &F) {}

fn main() {
    let factor = 2;
    let multiply = |x: i32| x * factor;
    
    assert_fn_with_args(&multiply);       // ✅ Fn(i32) -> i32
    assert_fn_mut_with_args(&multiply);   // ✅ FnMut(i32) -> i32
    assert_fn_once_with_args(&multiply);  // ✅ FnOnce(i32) -> i32
}
```

#### How it works

These functions don't do anything at runtime — they're zero-cost. The trait bound `F: Fn()` is checked entirely at compile time. If the closure doesn't implement the bound, you get a compile error like:

```
error[E0525]: expected a closure that implements the `Fn` trait,
              but this closure only implements `FnMut`
```

This is the same mechanism the standard library uses — when `thread::spawn` requires `FnOnce() + Send + 'static`, it's just a trait bound that the compiler checks.

## When Does the Compiler Apply a Copy?

Understanding when Rust copies vs. moves is essential for reasoning about closures, assignments, and function calls.

### The rule

> **A value is copied instead of moved when its type implements the `Copy` trait.**

That's it. There is no heuristic or analysis of "is this value used later." The compiler checks one thing: does `T: Copy`? If yes, every "move position" becomes a bitwise copy and the original remains valid. If no, it's a move and the original is invalidated.

### What implements `Copy`

`Copy` is an auto-derivable marker trait, but it has a strict requirement: a type can implement `Copy` **only if all of its fields also implement `Copy`**, and the type does **not** implement `Drop`.

| Type | `Copy`? | Why |
|------|---------|-----|
| `i32`, `f64`, `bool`, `char` | Yes | Primitives — bitwise copy is the whole value |
| `&T` (shared reference) | Yes | Just a pointer — copying the pointer is cheap and safe |
| `&mut T` | **No** | Mutable references are unique — copying would create aliasing |
| `*const T`, `*mut T` | Yes | Raw pointers are just addresses |
| `[T; N]` where `T: Copy` | Yes | Fixed-size array of `Copy` elements |
| `(A, B, C)` where all are `Copy` | Yes | Tuple of `Copy` elements |
| `String` | **No** | Owns heap allocation — needs `Clone`, not `Copy` |
| `Vec<T>` | **No** | Owns heap allocation |
| `Box<T>` | **No** | Unique ownership of heap data |
| `Rc<T>`, `Arc<T>` | **No** | Reference counting — needs `Clone` to bump count |
| `Option<T>` where `T: Copy` | Yes | Enum of `Copy` inner type |
| Any struct with `Drop` impl | **No** | `Copy` and `Drop` are mutually exclusive |

### Where copies happen

A copy occurs in any "move position" when `T: Copy`:

```rust
let a: i32 = 42;

// 1. Assignment — copy (i32: Copy)
let b = a;          // `a` is still valid
println!("{a}");     // OK

// 2. Function call — copy
fn takes_int(x: i32) { println!("{x}"); }
takes_int(a);        // `a` is copied into the parameter
println!("{a}");     // OK — still valid

// 3. Return — copy
fn ret() -> i32 { let x = 5; x }  // x is copied out

// 4. Pattern matching / destructuring — copy
let (x, y) = (a, a); // each use of `a` is a copy
```

Contrast with a non-`Copy` type:

```rust
let s = String::from("hello");

let t = s;           // MOVE — `s` is invalidated
// println!("{s}");  // ERROR: value used after move

fn takes_string(x: String) {}
// takes_string(s);  // would be a move if s were still valid
```

### Copy vs. Clone

`Copy` and `Clone` are related but distinct:

| | `Copy` | `Clone` |
|---|---|---|
| Mechanism | Implicit bitwise copy | Explicit `.clone()` call |
| When it happens | Automatically at every move position | Only when you write `.clone()` |
| Cost | Always cheap (memcpy) | Can be expensive (heap allocation, deep copy) |
| Requirement | All fields `Copy`, no `Drop` impl | Just needs `impl Clone` |
| Trait relationship | `Copy: Clone` (`Copy` is a subtrait of `Clone`) |

```rust
// Copy: happens implicitly
let a: i32 = 42;
let b = a; // copy — automatic, cheap

// Clone: must be explicit
let s = String::from("hello");
let t = s.clone(); // clone — explicit, allocates new heap buffer
println!("{s}");    // OK — s was cloned, not moved
```

### Copy semantics in closures

This interacts directly with closures and the `move` keyword:

#### Without `move` — `Copy` types are captured by reference (like everything else)

```rust
let x: i32 = 42; // i32: Copy
let f = || println!("{x}"); // captures &x (shared reference)
println!("{x}");             // x is still usable — it was only borrowed
f();
```

The compiler sees the closure only reads `x`, so it captures `&x`. No copy or move happens to `x` itself.

#### With `move` — `Copy` types are copied into the closure

```rust
let x: i32 = 42;
let f = move || println!("{x}"); // x is COPIED into the closure
println!("{x}");                  // STILL OK — i32 is Copy
f();
```

Because `i32: Copy`, the `move` keyword triggers a copy, not a destructive move. The original `x` remains valid. This is different from `move` with a non-`Copy` type:

```rust
let s = String::from("hello");
let f = move || println!("{s}"); // s is MOVED into the closure
// println!("{s}");              // ERROR: s was moved
f();
```

#### Desugared view

```rust
let x: i32 = 42;
let y = String::from("hello");
let f = move || println!("{x} {y}");
```

Desugars to approximately:

```rust
struct __Closure {
    x: i32,     // copied in (i32: Copy)
    y: String,  // moved in (String: !Copy)
}

// After the closure is created:
// `x` is still valid (was copied)
// `y` is invalid (was moved)
```

### When the compiler does NOT copy

Even if a type is `Copy`, there are contexts where no copy occurs:

```rust
let x: i32 = 42;

// No copy — just creating a reference:
let r = &x;  // r is &i32, x is untouched

// No copy — the variable is never "used in move position":
if x > 0 {   // comparison doesn't move or copy x
    // ...
}
```

Copies only happen when the value flows to a new binding, function parameter, or return value — i.e., when a "move" would otherwise occur.

### Implementing `Copy` for your own types

```rust
// Derive both Copy and Clone (Copy requires Clone):
#[derive(Copy, Clone)]
struct Point {
    x: f64,
    y: f64,
}

let a = Point { x: 1.0, y: 2.0 };
let b = a;  // copy — a is still valid
```

If any field is non-`Copy`, the derive fails:

```rust
#[derive(Clone)] // can derive Clone...
// #[derive(Copy)] // ERROR: String is not Copy
struct Named {
    name: String,
    id: u32,
}
```

### Why `Copy` and `Drop` are mutually exclusive

If a type implements `Drop`, it has custom destruction logic — something needs to happen beyond just forgetting the bits (e.g., freeing memory, closing a handle). If the compiler silently bitwise-copied such a type, both the original and the copy would run `Drop`, causing double-free or other resource bugs. Therefore, Rust enforces: **if you implement `Drop`, you cannot implement `Copy`**.

```rust
struct Resource { id: u32 }

impl Drop for Resource {
    fn drop(&mut self) { println!("freeing resource {}", self.id); }
}

// impl Copy for Resource {} // ERROR: cannot impl Copy for a type with Drop
```

### Summary table: what happens at each "use"

Given `let a: T = ...;`:

| Operation | `T: Copy` | `T: !Copy` |
|-----------|-----------|-------------|
| `let b = a;` | Copy — `a` still valid | Move — `a` invalidated |
| `foo(a);` | Copy — `a` still valid | Move — `a` invalidated |
| `let b = &a;` | Borrow — no copy | Borrow — no move |
| `let b = a.clone();` | Clone (= copy) — `a` valid | Clone — `a` valid |
| `let b = &a` in closure (no `move`) | Borrow — no copy | Borrow — no move |
| `move` closure captures `a` | Copy — `a` still valid | Move — `a` invalidated |

## Summary: Decision Flowchart

```
Does the closure need to outlive the current scope?
├── YES (e.g., returned, spawned in a thread, stored in a struct)
│   └── Use `move` to transfer ownership into the closure.
│       ├── Need shared (concurrent) access? → Box<dyn Fn(...)> or impl Fn(...)
│       └── Called only once? → impl FnOnce(...)
└── NO (used locally)
    └── Let the compiler choose capture modes automatically.
        ├── Body only reads captures → implements Fn + FnMut + FnOnce
        ├── Body mutates captures → implements FnMut + FnOnce
        └── Body moves out of captures → implements only FnOnce
```

### Rules of thumb

1. **The compiler picks the minimal capture mode** — `move` forces by-value capture for all variables.
2. **`move` does not determine which trait is implemented** — only the closure body does.
3. **Use `move` when the closure must outlive the captured data's scope** — returning closures, spawning threads, async blocks.
4. **`move` is explicit by design** — Rust requires ownership transfers to be visible at the call site.
5. **Prefer `FnOnce` in trait bounds** unless you need repeated calls — it accepts the widest range of closures.
6. **Non-capturing closures can coerce to `fn` pointers** — capturing closures cannot.
